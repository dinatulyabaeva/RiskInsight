# Архитектура и границы доверия

## Компоненты

`app/main.py` обслуживает Web UI и JSON API. Bootstrap создает синтетическую БД, затем все пользовательские чтения идут через MCP. На каждый запрос дашборда или агента открывается отдельная MCP-сессия с новым child process; все вызовы одного анализа используют одну сессию. Concurrency ограничен semaphore, по умолчанию 2. Это простой жизненный цикл для MVP, но имеет накладные расходы запуска процесса.

`app/mcp_client.py` выполняет initialize, проверяет версию/capabilities, отправляет notifications/initialized и последующие запросы с id. Запросы сериализуются lock. При закрытии завершается stdin; далее wait/terminate/kill с тайм-аутами. Секреты LLM и токен Web API не наследуются дочерним процессом. stdout читается только как JSON-RPC.

`app/mcp_server.py` — небольшая реализация MCP revision 2025-06-18. Tools и resources — поддерживаемый поднабор. Валидация аргументов через `tool_registry.py`; вызовы направляются в `Analytics`. Неизвестный tool возвращает protocol error, ошибки пользовательских аргументов — tool execution result с isError=true. Нет remote HTTP, публичного MCP-порта, произвольных файлов, SQL или команд.

`app/analytics.py` открывает SQLite URI `mode=ro` и устанавливает `query_only`. Группировки выбираются из allowlist. Values передаются bound parameters. Для сумм используются копейки. Структурированные результаты компактны и содержат provenance, filters, dates, unit conventions.

`app/agent.py` получает schemas через tools/list и передает их модели. Tool-call arguments JSON разбираются, неизвестные tools не вызываются. Каждый реально выполненный вызов добавляет [Tn], аргументы, результат, success/error и длительность. Неудачные tool calls тоже остаются в журнале.

`static/app.js` отображает дашборд и ответ безопасными текстовыми DOM-узлами. Источники [Tn] открывают соответствующий фактический trace. Экспорт формируется локально в браузере без отправки данных третьим лицам. Ключ LLM никогда не попадает в браузер.

## Два режима

В LLM-моде основная логика выбора аналитических действий и интерпретации находится в модели. Python считает числа, а не пытается предсказывать намерения по ключевым словам.

В DEMO действия задаются явным enum сценария. Пользовательский свободный вопрос не интерпретируется. Отчеты шаблонные, но MCP, SQLite и метрики настоящие. Нельзя считать DEMO доказательством успешной интеграции внешней модели.

## Доверие и ограничения

Область анализа из UI является default, а не security boundary: это общий синтетический портфель. Модель может выбрать другую область при явном запросе пользователя и должна описать ее. Требований per-user row-level security нет и их реализация не заявляется.

История чата только визуальная: предыдущие ответы не передаются модели. Это исключает неявное переиспользование устаревших source refs и упрощает аудит одного запроса. Цена — отсутствие полноценного многотурового разговора; вопрос должен быть самодостаточным.

MCP stdio выбран для приватного внутриконтейнерного взаимодействия. Для удаленного сервера потребуются официальный HTTP-транспорт, аутентификация, Origin checks и отдельные интеграционные тесты. Называть `/api/chat` MCP endpoint нельзя.

## Поведение при сбоях

Нет доступного среза -> ошибка, не подмена последним. Пустая допустимая выборка -> нулевой остаток и null доли. Неверная LLM-конфигурация -> 503; upstream API/формат -> 502; общий тайм-аут -> 504; исчерпанная квота -> 429. При протокольном сбое MCP -> 503. Необработанные ошибки инфраструктуры требуют проверки серверного лога; пользователь не получает секретов или stack trace через штатные сообщения.

MCP stderr не передается в UI; встроенный клиент его отбрасывает, чтобы не блокироваться на pipe. Для диагностики запустите сервер отдельно с SDK/Inspector и просмотром stderr. Это ограничение наблюдаемости MVP.
